12 — RisingWave (base de données de streaming)

Note

Statut : ✅ installé · Date : 2026-11-11

Objectif

RisingWave : base SQL de streaming (compatible avec le protocole PostgreSQL). Elle maintient des vues matérialisées incrémentales sur des flux (Kafka, CDC PostgreSQL…) ou des tables.

Elle est installée avec l’opérateur RisingWave, dans un namespace dédié, et s’appuie sur l’infrastructure existante :

Rôle RisingWaveNotre système
Meta store (catalogue, métadonnées)PostgreSQL pg-main (CNPG), base risingwave, rôle risingwave
State store (Hummock : état et données)Garage S3, bucket risingwave

Prérequis

  • 07 — PostgreSQL (CloudNativePG)
  • 09 — Stockage objet S3 (Garage)
  • cert-manager (installé avec le cluster, utilisé par le webhook de l’opérateur)

Installation 

make sync SELECTOR=name=garage             # hook postsync : bucket + clé + secret s3-risingwave
make apply SELECTOR=name=pg-main           # rôle + base risingwave
make apply SELECTOR=name=risingwave-operator
make apply SELECTOR=name=risingwave

(ou simplement make sync, l’ordre est géré par needs).

Licence d’essai intégrée (notre cas)

Une nouvelle installation embarque une clé par défaut. Elle débloque toutes les fonctions Premium, mais uniquement sur un petit cluster :

ÉlémentValeur (vérifiée sur notre instance)
Clérw-default-all-4-core, tier: all, paramètre système license_key = <default>
Limite4 RWU = 4 cœurs CPU et 16 Gio de mémoire au total (1 RWU = 1 cœur + 4 Gio)
Expirationexp: 10000627200 (an 2286) : pas d’expiration en pratique
Ce qui est comptéles ressources de tous les nœuds (meta, frontend, compute, compactor), lues depuis les limites cgroup des pods. Sans limite, c’est le CPU de l’hôte (16 × 4 = 64)
Notre consommation3 cœurs / 8 Gio (make rw-license)

Si la limite est dépassée : les fonctions Premium sont désactivées, pour les jobs existants comme pour les nouveaux, jusqu’à l’installation d’une clé payante. Le moteur Community continue de fonctionner.

⚠️ Conséquence pour ce projet : notre source CDC utilise CREATE SECRET (Premium, voir 13). Si on augmente les replicas ou les limites CPU/mémoire au-delà de 4 cœurs ou 16 Gio, le secret n’est plus utilisable. → Contrôler make rw-license après tout redimensionnement, ou basculer la source CDC vers un mot de passe en clair (voir plus bas).

Ce qui reste libre (Community, Apache 2.0)

Le moteur de streaming et ce que nous utilisons hors secrets :

  • tables, vues matérialisées incrémentales, jointures, agrégations, fenêtres ;
  • protocole PostgreSQL (psql, pgAdmin, pilotes JDBC, etc.) ;
  • state store S3 (Garage) et meta store PostgreSQL ;
  • source CDC PostgreSQL (postgres-cdc) et MySQL. Seule la propagation automatique des changements de schéma (CdcAutoSchemaChange) est Premium : sans elle, un ALTER TABLE côté pg-main doit être reporté à la main côté RisingWave ;
  • les autres connecteurs courants (Kafka, sinks PostgreSQL, S3, Iceberg avec catalogues non-Glue…) : aucun n’apparaît dans rw_features.

Rester 100 % Community (sans fonction Premium)

Si le cluster doit dépasser 4 cœurs / 16 Gio sans clé payante :

  1. Remplacer le secret par le mot de passe dans la source CDC (password = '…' au lieu de password = SECRET pg_main_cdc_password). Le mot de passe est alors visible par SHOW CREATE SOURCE et stocké en clair dans le catalogue (base risingwave de pg-main). C’est acceptable en labo, avec le rôle rw_cdc en lecture seule.
  2. Reporter manuellement les changements de schéma des tables CDC.
  3. Vérifier avec SELECT name FROM rw_features WHERE available; qu’aucun job ne dépend d’une fonction Premium.

Installer une clé payante (si besoin)

  • Opérateur : clé dans un Secret Kubernetes, référencée par la ressource RisingWave (les mises à jour du Secret sont propagées automatiquement) ;
  • ou variable RW_LICENSE_KEY / fichier RW_LICENSE_KEY_PATH sur le nœud meta ;
  • ou ALTER SYSTEM SET license_key TO '…'; (à renouveler soi-même avant expiration).
  • Revenir à la clé d’essai : ALTER SYSTEM SET license_key TO DEFAULT;

Vérification (testée le 2026-11-11) 

CREATE TABLE orders (id INT PRIMARY KEY, customer VARCHAR, amount NUMERIC, ts TIMESTAMPTZ DEFAULT now());
CREATE MATERIALIZED VIEW revenue_by_customer AS
  SELECT customer, count(*) AS n, sum(amount) AS total FROM orders GROUP BY customer;
INSERT INTO orders (id, customer, amount) VALUES (1,'alice',10),(2,'bob',5),(3,'alice',7.5);
FLUSH;
SELECT * FROM revenue_by_customer;      -- alice 17.5 / bob 5
INSERT INTO orders (id, customer, amount) VALUES (4,'bob',20);
FLUSH;
SELECT * FROM revenue_by_customer;      -- bob passe à 25 (mise à jour incrémentale)

Pièges rencontrés

  • Licence gratuite limitée à 4 cœurs : sans limite CPU, chaque composant voit les 16 cœurs de l’hôte (64 au total). Les fonctions sous licence, comme CREATE SECRET, sont alors refusées. → Limites CPU dont la somme reste ≤ 4 (SELECT type, system_total_cpu_cores FROM rw_worker_nodes). Voir la section Licence et 13.

  • Port du frontend : 4567, et non 4566 (valeur de la doc RisingWave) : l’opérateur v0.18 publie 4567 (SQL), 4560 (HTTP) et 8080 (métriques).

  • role "risingwave" does not exist sur la ressource Database au premier apply : la base a été créée avant le rôle. CNPG réessaie tout seul et l’erreur disparaît en quelques secondes.

  • La CRD RisingWave n’existe qu’après l’installation de l’opérateur : disableValidationOnInstall: true + needs sur la release.

  • Garage impose le path-style et la région garage : forcePathStyle: true et region: garage dans stateStore.s3.

  • make recreate : le meta store vit dans pg-main et le state store dans Garage. Après une recréation, il faut restaurer pg-main (10) pour que le catalogue RisingWave corresponde au contenu du bucket.
