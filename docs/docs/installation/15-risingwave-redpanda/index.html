15 — RisingWave ⇄ Redpanda (source et sink Kafka)

15 — RisingWave ⇄ Redpanda (source et sink Kafka)

Note

Statut : ✅ installé · Date : 2026-11-11

Objectif

Brancher RisingWave sur Redpanda :

  • Source Kafka : RisingWave lit en continu les événements JSON du topic shop-events ;
  • Vues matérialisées : agrégats par fenêtre de temps, et jointure du flux Kafka avec les tables CDC de pg-main (13) ;
  • Sink Kafka : chaque mise à jour d’une vue est republiée dans Redpanda (topic shop-activity-by-city), consommable par d’autres applications.
                 Redpanda                          RisingWave                                Redpanda
 producteurs ─▶  shop-events  ──(source kafka)──▶  shop_events ─┬▶ shop_events_per_minute (TUMBLE 1 min)
                                                                └▶ shop_activity_by_city ──(sink upsert)──▶ shop-activity-by-city
 pg-main/app ─(CDC, étape 13)─▶ app_customers ──────────────────────┘ (jointure par customer_id)

Tous les connecteurs utilisés (source Kafka, sink Kafka, FORMAT PLAIN/UPSERT ENCODE JSON) font partie de l’édition Community de RisingWave (aucun n’apparaît dans rw_features, voir 12 — Licence).

Prérequis

  • 12 — RisingWave (base de données de streaming), 13 — CDC pg-main → RisingWave (table app_customers)
  • 14 — Redpanda (streaming compatible Kafka) + Redpanda Console

Installation 

make rp-topics           # topics shop-events et shop-activity-by-city (3 partitions, réplication 3)
make rw-kafka-setup      # source, vues, sink dans RisingWave (idempotent)
make rp-demo-events N=60 # événements de démo
make rw-kafka-status     # vues + derniers messages du sink
FichierRôle
deploy/k8s/sql/risingwave/20-kafka-redpanda.sqlCREATE SOURCE, CREATE MATERIALIZED VIEW ×2, CREATE SINK
deploy/k8s/scripts/rp-demo-events.shproducteur de démo (via rpk topic produce dans redpanda-0)

Format des événements (shop-events) 

{"event_id":"…uuid…","customer_id":2,"event_type":"purchase","amount":120,"event_time":"2026-11-11T20:59:12Z"}

customer_id (1 à 4) correspond aux clients de pg-main/app.customers. event_type vaut view, cart ou purchase.

Objets RisingWave 

CREATE SOURCE shop_events (event_id VARCHAR, customer_id INT, event_type VARCHAR,
                           amount NUMERIC, event_time TIMESTAMPTZ)
WITH (connector = 'kafka', topic = 'shop-events',
      properties.bootstrap.server = 'redpanda.redpanda.svc.cluster.local:9093',
      scan.startup.mode = 'earliest')
FORMAT PLAIN ENCODE JSON;

CREATE MATERIALIZED VIEW shop_events_per_minute AS
  SELECT window_start, event_type, count(*) AS events, sum(amount) AS amount
  FROM TUMBLE(shop_events, event_time, INTERVAL '1 minute')
  GROUP BY window_start, event_type;

CREATE MATERIALIZED VIEW shop_activity_by_city AS
  SELECT c.city, count(*) FILTER (WHERE e.event_type = 'view') AS views, …
  FROM shop_events e JOIN app_customers c ON e.customer_id = c.id
  GROUP BY c.city;

CREATE SINK shop_activity_by_city_sink FROM shop_activity_by_city
WITH (connector = 'kafka', topic = 'shop-activity-by-city',
      properties.bootstrap.server = 'redpanda.redpanda.svc.cluster.local:9093',
      primary_key = 'city')
FORMAT UPSERT ENCODE JSON;
  • Source partagée (shared source) : un seul consommateur Kafka alimente toutes les vues construites sur shop_events. D’où le message snapshot backfill disabled due to using shared source, qui est normal.
  • La source ne stocke pas les événements dans RisingWave : seules les vues matérialisent un état. Pour interroger les événements bruts, utiliser CREATE TABLE … WITH (connector='kafka', …) à la place de CREATE SOURCE.
  • Sink upsert : message avec clé {"city": …} et valeur = ligne complète. Quand une ligne disparaît de la vue, le sink publie un tombstone (valeur nulle) pour cette clé.

Ajouter un flux

  1. make rp-topics RP_TOPICS="mon-topic" (ou laisser la création automatique)
  2. Ajouter CREATE SOURCE … topic = 'mon-topic' … et les vues dans un nouveau fichier deploy/k8s/sql/risingwave/30-….sql (avec IF NOT EXISTS)
  3. L’appliquer avec la même commande que make rw-kafka-setup, en changeant le fichier.

Autres formats : ENCODE AVRO / ENCODE PROTOBUF avec le Schema Registry de Redpanda (schema.registry = 'http://redpanda.redpanda.svc.cluster.local:8081').

Pièges rencontrés

  • rpk topic consume -n 4 attend indéfiniment s’il y a moins de 4 messages. Pour lire jusqu’à la fin puis s’arrêter : -o :end (utilisé par make rw-kafka-status).
  • Connexion en PLAINTEXT sans SASL (configuration de labo de Redpanda, voir 14). Si on active SASL/TLS, ajouter properties.security.protocol, properties.sasl.mechanism, properties.sasl.username / password dans la source et le sink.
  • Rétention : shop-events garde les messages selon la rétention par défaut de Redpanda, sur des PVC de 10 Gi. Avec scan.startup.mode = 'earliest', une source recréée relit tout ce qui reste dans le topic.

Désinstallation 

DROP SINK shop_activity_by_city_sink;
DROP MATERIALIZED VIEW shop_activity_by_city;
DROP MATERIALIZED VIEW shop_events_per_minute;
DROP SOURCE shop_events;
make rpk ARGS="topic delete shop-events shop-activity-by-city"
