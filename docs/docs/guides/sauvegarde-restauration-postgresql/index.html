Sauvegarde et restauration PostgreSQL ⇄ S3

Note

Mode opératoire testé le 2026-11-11 sur pg-main (PostgreSQL 17, CloudNativePG) et Garage S3 (bucket cnpg-backups).

Deux mécanismes complémentaires envoient les données de pg-main vers le S3 Garage, et permettent de les en ramener :

Logique, par schéma (ce guide)Physique, instance complète (étape 10)
Outilpg_dump / pg_restore (format custom)barman-cloud (plugin CNPG)
Granularitéun schéma d’une basetoute l’instance (toutes les bases)
Déclenchementà la demande : make pg-backupcontinu (WAL) + quotidien 02:00
Restaurationdans la base d’origine ou une autre base, sans arrêtnouveau cluster CNPG
Point de restaurationl’instant du dumpn’importe quel instant (PITR)
Emplacement S3s3://cnpg-backups/logical/<base>/<schéma>/<horodatage>.dumps3://cnpg-backups/pg-main/
Cas d’usageerreur applicative sur un schéma, copie vers une autre base, archivage, migrationperte de l’instance, make recreate, retour à un instant précis

Quelle méthode choisir ? 

    flowchart TD
  Q{Que faut-il récupérer ?}
  Q -->|Un schéma abîmé : tables supprimées,<br/>données corrompues par l'application| L1[Restauration logique du schéma<br/>make pg-restore DB=… SCHEMA=…]
  Q -->|Vérifier une sauvegarde ou copier<br/>un schéma vers une autre base| L2[Restauration logique vers une autre base<br/>make pg-restore … TARGET=autre_base]
  Q -->|Toute l'instance : cluster perdu,<br/>make recreate| P1[Restauration physique<br/>nouveau Cluster CNPG + barman]
  Q -->|Revenir à un instant précis<br/>avant une erreur, toutes bases confondues| P2[PITR physique<br/>recoveryTarget.targetTime]
  L1 --> OK([Sans arrêt de pg-main])
  L2 --> OK
  P1 --> NC([Nouveau cluster, bascule des applications])
  P2 --> NC

Déroulement

Chaque sauvegarde est un Job Kubernetes éphémère dans le namespace databases. Il ne s’exécute pas sur le poste local, donc rien ne transite par la machine hôte.

    sequenceDiagram
  autonumber
  actor Op as Opérateur
  participant Mk as make pg-backup
  participant Job as Job pg-backup-app-ventes
  participant Dump as initContainer pg-dump<br/>(postgres:17-alpine)
  participant Vol as emptyDir /work
  participant Up as conteneur upload<br/>(amazon/aws-cli)
  participant PG as pg-main-rw
  participant S3 as Garage S3

  Op->>Mk: DB=app SCHEMA=ventes
  Mk->>Job: kubectl apply (secrets pg-main-superuser, s3-cnpg)
  Job->>Dump: démarrage
  Dump->>PG: le schéma existe ? (pg_namespace)
  Dump->>PG: pg_dump --schema=ventes --format=custom (TLS)
  PG-->>Dump: snapshot cohérent du schéma
  Dump->>Vol: /work/dump (compressé)
  Job->>Up: démarrage (après succès du dump)
  Up->>S3: aws s3 cp → logical/app/ventes/<horodatage>.dump
  S3-->>Up: 200 OK
  Up-->>Mk: logs (taille, clé S3)
  Mk->>Job: suppression du Job
  Mk-->>Op: [ ok ] Sauvegarde : s3://…

Points clés :

  • Cohérence : pg_dump travaille dans une transaction REPEATABLE READ. Le dump est cohérent même si l’application écrit en même temps, sans bloquer les lectures ni les écritures. Il prend seulement des verrous ACCESS SHARE, qui bloquent les DROP et ALTER concurrents.
  • Contenu : tables, données, index, contraintes (clés étrangères incluses), vues, séquences, fonctions du schéma, propriétaires et droits.
  • Pas de transfert inutile : l’upload ne démarre que si le dump a réussi (initContainer). Un dump en échec ne laisse donc aucun fichier partiel dans S3.

Restauration logique d’un schéma (S3 → PostgreSQL) 

make pg-restore DB=app SCHEMA=ventes                            # dernière sauvegarde
make pg-restore DB=app SCHEMA=ventes FILE=20261111T215554Z.dump # sauvegarde précise
make pg-restore DB=app SCHEMA=ventes TARGET=app_verif           # dans une autre base (créée si besoin)

Warning

La restauration remplace entièrement le schéma dans la base cible (DROP SCHEMA … CASCADE, puis recréation). Tout ce qui a été écrit dans ce schéma depuis la sauvegarde est perdu. Les objets d’autres schémas qui en dépendent (vues, clés étrangères) sont aussi supprimés par le CASCADE. En cas de doute, restaurer d’abord dans une autre base avec TARGET=… et comparer.

    sequenceDiagram
  autonumber

  Mk->>Job: kubectl apply
  Job->>Dl: démarrage
  Dl->>S3: aws s3 cp <clé> /work/dump
  S3-->>Dl: dump
  Dl->>Vol: /work/dump
  Job->>Rs: démarrage (après succès du téléchargement)
  Rs->>PG: base cible absente ? → CREATE DATABASE
  rect rgb(230, 240, 255)
    Note over Rs,PG: UNE SEULE TRANSACTION (psql --single-transaction, ON_ERROR_STOP)
    Rs->>PG: BEGIN
    Rs->>PG: DROP SCHEMA IF EXISTS ventes CASCADE
    Rs->>PG: CREATE SCHEMA, tables, données (COPY), index, FK, vues, droits
    alt tout s'est bien passé
      Rs->>PG: COMMIT → nouveau schéma visible d'un coup
    else une erreur
      Rs->>PG: ROLLBACK → l'ancien schéma est intact
    end
  end
  Rs-->>Mk: « tables restaurées : N »
  Mk-->>Op: [ ok ] Restauration terminée

Pourquoi cet enchaînement :

  • Téléchargement d’abord : si le fichier S3 est absent ou illisible, le Job échoue avant de toucher à la base.
  • Tout ou rien : la suppression et la recréation sont dans la même transaction. Les applications voient l’ancien schéma jusqu’au COMMIT, puis le nouveau. Il n’y a jamais d’état intermédiaire et pas de schéma à moitié restauré.
  • Propriétaires conservés : les rôles (app, …) existent dans le même cluster, donc les objets retrouvent leur propriétaire d’origine.

Contrôles utiles après une restauration :

-- nombre de lignes par table du schéma
SELECT relname, n_live_tup FROM pg_stat_user_tables WHERE schemaname = 'ventes';
-- propriétaires
SELECT tablename, tableowner FROM pg_tables WHERE schemaname = 'ventes';
-- contraintes
SELECT conname, contype FROM pg_constraint WHERE connamespace = 'ventes'::regnamespace;

Restauration physique (instance complète, PITR)

Quand c’est toute l’instance qu’il faut récupérer (cluster perdu, make recreate, retour à un instant précis), on utilise les sauvegardes physiques barman. La procédure détaillée et testée est dans l’étape 10.

    flowchart LR
  S3[(s3://cnpg-backups/pg-main<br/>base/ + wals/)] --> R[Nouveau Cluster CNPG<br/>bootstrap.recovery<br/>source: origin]
  R --> B1[1. Télécharge la sauvegarde de base<br/>la plus récente avant la cible]
  B1 --> B2[2. Rejoue les WAL jusqu'à<br/>la fin, ou jusqu'à targetTime]
  B2 --> B3[3. Promotion : nouvelle timeline]
  B3 --> APPS[Bascule des applications<br/>vers le nouveau service -rw]
  
bootstrap:
  recovery:
    source: origin
    recoveryTarget:
      targetTime: "2026-11-11 21:50:00+00"   # optionnel : sinon, jusqu'au dernier WAL archivé
externalClusters:
  - name: origin
    plugin:
      name: barman-cloud.cloudnative-pg.io
      parameters: {barmanObjectName: pg-main-backups, serverName: pg-main}

On peut aussi combiner les deux méthodes. Par exemple, restaurer l’instance à un instant donné dans un cluster temporaire, en extraire un seul schéma avec pg_dump -n, puis le restaurer dans pg-main avec ce guide.

Pièges et limites

  • Même version majeure : le dump est fait avec pg_dump 17 (postgres:17-alpine), comme pg-main. Un pg_dump plus ancien que le serveur refuse de fonctionner. Pour restaurer vers une version plus récente, c’est possible.
  • Ce que -n schéma n’emporte pas : les rôles (globaux au cluster), les extensions créées dans un autre schéma, les large objects, les objets d’autres schémas qui référencent celui-ci. Pour une base entière, utiliser plutôt pg_dump sans -n, ou la méthode physique.
  • Dépendances inter-schémas : le DROP SCHEMA … CASCADE supprime aussi les vues et les clés étrangères des autres schémas qui pointent vers le schéma restauré, et ces objets ne sont pas recréés. Vérifier avant avec : SELECT * FROM pg_depend ou en restaurant d’abord dans une base de test.
  • CDC vers RisingWave (étape 13) : la réplication logique ne transmet pas les DDL. Si un schéma contenant des tables répliquées est restauré, le DROP n’est pas propagé, et les données rechargées arrivent comme des INSERT. Il faut alors recréer les tables CDC côté RisingWave. Le schéma ventes de démonstration n’est pas répliqué.
  • Restauration sur le primaire : le Job vise pg-main-rw. Les réplicas reçoivent la restauration par la réplication physique, sans action.
  • Rétention : les dumps logiques ne sont pas purgés automatiquement, contrairement aux sauvegardes barman (14 jours). Les supprimer avec garage-webui (https://garage.k8s.test, bucket cnpg-backups, dossier logical/).
  • Volumétrie : le dump transite par un volume emptyDir du pod, donc sur le disque du nœud. Pour un très gros schéma, prévoir l’espace, ou passer en streaming (pg_dump | aws s3 cp - s3://…).
  • Test à ne pas reproduire : enchaîner DROP SCHEMA et pg_dump du même schéma dans une même transaction crée un interblocage. pg_dump attend le verrou que tient la transaction. Le script évite ce piège : le fichier est téléchargé avant l’ouverture de la transaction.
